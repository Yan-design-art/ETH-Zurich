1. ПРОБЛЕМА МОНОЛИТНОГО КОДА
--------------------------------------------------------------------------------
В исходной реализации вся логика игры (генерация чисел, игровой процесс, подсчет 
очков, определение победителя и вывод на экран) находилась внутри функции main(). 

Такой код невозможно протестировать автоматически по трем причинам:
- Жесткая связь с вводом-выводом (I/O): Потоки std::cout и функция _getch() 
  блокируют выполнение, ожидая действий человека. Тест не умеет нажимать кнопки.
- Непредсказуемость (Рандом): Генератор std::mt19937 выдает случайные значения. 
  Базовый unit-тест должен быть на 100% предсказуемым и детерминированным.
- Единственность main(): В проекте C++ может быть только одна точка входа main. 
  У фреймворка тестов есть своя функция main. Если логика заперта в вашей main, 
  тестовый проект не сможет вызвать её из-за конфликта имен.

2. ПРИНЦИП ИЗОЛЯЦИИ ЛОГИКИ (РЕФАКТОРИНГ)
--------------------------------------------------------------------------------
Для решения проблемы мы применили рефакторинг — изменили структуру кода, 
не меняя его поведение. Мы вынесли чистую логику сравнения результатов 
в отдельный заголовочный файл "game.h".

Почему именно заголовочный файл (.h)?
Написав функцию с ключевым словом "inline" в файле .h, мы сделали её общей. 
Теперь один и тот же файл обслуживает два независимых фронта:
1. Основная игра — подключает game.h, берет случайные числа и отдает функции.
2. Тестовый проект — подключает game.h, подставляет жесткие, заранее известные 
   данные и проверяет корректность работы.

Для строгости и читаемости мы заменили «магические числа» на перечисление:
enum class RoundResult { PlayerWins, AIWins, Draw };

Выделенная функция стала «черным ящиком»: она принимает два числа и возвращает 
строго один из трех вариантов RoundResult. Она ничего не знает про консоль и рандом.

3. СТРУКТУРА МАКРОСА TEST И ИМЕНОВАНИЕ ТЕСТОВ
--------------------------------------------------------------------------------
Строка вида TEST(DiceGameLogic, PlayerShouldWin) — это объявление тестовой 
функции. Макрос TEST принимает ровно два параметра:

1. Первый параметр (например, DiceGameLogic) — Имя Тест-Кейса (Набор тестов).
   Это общее название для группы тестов, проверяющих один компонент. В интерфейсе
   Обозревателя тестов (Test Explorer) это имя отображается как общая «папка».
   
2. Второй параметр (например, PlayerShouldWin) — Имя конкретного Теста.
   Это уникальное название проверки внутри группы. Оно должно четко описывать 
   ситуацию на английском языке (например, "Игрок должен победить"). Если тест 
   упадет, по этому имени вы сразу поймете, какой именно сценарий сломался.

В Обозревателе тестов это выстраивается в понятную иерархию:
▼ GameTests (Тестовый проект)
   ▼ DiceGameLogic (Имя тест-кейса / папка)
      ├── PlayerShouldWin (Тест 1: Игрок побеждает)
      └── AIShouldWin     (Тест 2: ИИ побеждает)

4. АНАТОМИЯ UNIT-ТЕСТА (ШАБЛОН AAA) И СИСТЕМА ПРОВЕРКИ
--------------------------------------------------------------------------------
Каждая автоматическая проверка пишется по строгому стандарту AAA:
- Arrange (Подготовка): Создаем контролируемые входные данные.
- Act (Действие): Вызываем тестируемую функцию.
- Assert (Проверка): Сравниваем полученный результат с ожидаемым.

Главный инструмент проверки — макрос EXPECT_EQ(Аргумент_1, Аргумент_2). 
Он расшифровывается как "Expect Equal" (Ожидаю, что равны). 

Как он работает внутри:
- Если Аргумент_1 равен Аргумент_2: Тест сообщает Обозревателю тестов, что проверка 
  прошла успешно. В интерфейсе загорается ЗЕЛЕНАЯ галочка.
- Если они НЕ равны: Тест прерывается, загорается КРАСНЫЙ маркер, а в отчет 
  выводится подробная ошибка (например: "Ожидалось: AIWins, но функция вернула: 
  PlayerWins").

Пример готового теста:
TEST(DiceGameLogic, AIShouldWin) {
    // Arrange: У ИИ очков гарантированно больше
    int player_dice = 5;
    int ai_dice = 10;

    // Act: Запускаем изолированную функцию
    RoundResult result = determine_round_winner(player_dice, ai_dice);

    // Assert: Проверяем, совпадает ли реальный результат с ожидаемым
    EXPECT_EQ(result, RoundResult::AIWins);
}

5. ОСОБЕННОСТИ ЭКОСИСТЕМЫ VISUAL STUDIO И КОМПИЛЯТОРА MSVC
--------------------------------------------------------------------------------
1. Предкомпилированные заголовки (pch.h)
Это служебный файл для ускорения сборки. Компилятор один раз собирает тяжелые 
системные библиотеки (включая gtest) и кэширует их. 
ПРАВИЛО: Если в проекте включены предкомпилированные заголовки, строка 
#include "pch.h" ОБЯЗАНА идти самой первой строчкой кода в каждом .cpp файле. 
Иначе возникнет критическая ошибка C1010.

2. Ошибки линковщика (LNK2019 / LNK1120)
Возникают, если в решении есть старые, пустые или сломанные проекты, которые 
мешают общей сборке. Чтобы они не мешали, нужно собирать конкретный тестовый 
проект отдельно (Правый клик по проекту GameTests -> Сборка / Build), а затем 
запускать проверки через окно «Обозреватель тестов» (Test Explorer).

6. ГЛАВНЫЙ ИТОГ
--------------------------------------------------------------------------------
Вы разделили интерфейс (вывод на экран) и бизнес-логику (правила игры). Теперь у 
вас есть «робот-контролер». Если в будущем вы случайно сломаете код игры при 
добавлении новых функций, вам не придется вручную разыгрывать десятки раундов. 
Достаточно нажать «Запустить все тесты» — и система за долю секунды проверит все 
комбинации и покажет, всё ли в порядке.
